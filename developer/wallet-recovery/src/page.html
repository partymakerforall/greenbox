BEFORE REAL USE

What this prototype does—and what still needs a real test.

Everything happens in this page

No CDN code, analytics, uploads, or browser storage. The extension and hardware-wallet software have their own network behavior. Signatures and keys are held in memory; JavaScript cannot guarantee perfect memory erasure.

One card, future backups

The public card and package preserve the account, signing method, and exact key recipe. Save the cards or load them from a saved package when creating another backup. Earlier packages retain their original recipe automatically.

What key reuse means

The same account and signing method reuse one Greenbox encryption key across backups. If that derived key or its private signature leaks, the attacker can open that custodian’s share in every package using the key, including future ones. It still takes the required number of shares to recover a backup.

Hardware and restoration

Use the Trezor account paired in Rabby or MetaMask. MetaMask documents personal_sign for Trezor, so choose Readable message there. Safe 7 requires Trezor Suite and a compatible current extension. Physical Safe 3/5/7 signing and restoration have not been tested here. Rehearse with a spare/restored wallet and dummy data; never erase your only working device for a test.

Security limits

This integration has not had an independent security audit. It uses classical X25519 and Ethereum signatures; it is not post-quantum. Any threshold of custodians can cooperate at any time. Smart-contract multisigs are not supported.

The package format is specific to this prototype. It is not an age or SLIP-0039 file. If you recover bundle.tar, extract its keys, verify vault.age with minisign, then decrypt with age. Your existing owner passphrase recovery stays separate. A matching receipt must come from a trusted source; it is not a creator signature.
